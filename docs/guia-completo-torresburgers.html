1. Visão geral

O TorresBurgers é um sistema de delivery com três aplicações principais: API backend em NestJS, painel/web de cliente e administração em React/Vite, e aplicativo mobile em React Native/Expo. A API centraliza autenticação, produtos, adicionais, pedidos, endereços, status da loja, pagamentos, promoções e upload de imagens.

Camada Tecnologias Responsabilidade
Backend NestJS 11, TypeScript, TypeORM, PostgreSQL, JWT, Bcrypt, Sharp, Swagger API REST, regras de negócio, autenticação, banco, uploads, pagamentos e integrações externas.
Web React 19, Vite 7, TailwindCSS 4, Axios, Recharts, Lucide, Mercado Pago SDK Cardápio do cliente, carrinho, checkout, perfil, pedidos, dashboard administrativo e gestão de cardápio/equipe.
Mobile Expo 54, React Native 0.81, NativeWind, AsyncStorage, React Navigation, Axios Experiência mobile de cliente e painel admin simplificado, com configuração de API via túnel Serveo.
Estado real do código: algumas configurações ainda estão hardcoded. O backend sempre escuta em 3000; o web usa http://localhost:3000 diretamente em frontend-web/src/services/api.ts; o mobile usa uma URL Serveo diretamente em frontend-mobile/src/services/api.ts, atualizada pelo script npm run tunnel.

2. Checklist de execução rápida

Este é o caminho curto para outro desenvolvedor subir tudo localmente.

1. Clonar o projeto

git clone <URL_DO_REPOSITORIO>
cd TorresBurguers

2. Preparar PostgreSQL

createdb -U postgres torresburgers

Se o usuário/senha forem diferentes, ajuste o arquivo backend/.env.

3. Configurar backend

cd backend
npm install

Crie backend/.env:

DB_HOST=localhost
DB_PORT=5432
DB_USERNAME=postgres
DB_PASSWORD=0000
DB_DATABASE=torresburgers

JWT_SECRET=troque_esta_chave_por_um_valor_grande_e_secreto
FOOTBALL_DATA_TOKEN=opcional_token_football_data

4. Subir a API

npm run start:dev

A API ficará em http://localhost:3000 e o Swagger em http://localhost:3000/api.

5. Criar primeiro usuário admin

Em banco novo não há seed. Crie o admin pela rota pública de usuários:

curl -X POST http://localhost:3000/users \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Admin Torres",
    "email": "admin@torresburgers.com",
    "phone": "21999999999",
    "password": "SenhaAdmin123!",
    "role": "ADMIN"
  }'

6. Subir frontend web

cd ../frontend-web
npm install
npm run dev

Abra a URL exibida pelo Vite, normalmente http://localhost:5173.

7. Subir mobile

cd ../frontend-mobile
npm install
npm run tunnel
npm run start

Use npm run tunnel em uma janela de terminal para expor a API local via Serveo e atualizar frontend-mobile/src/services/api.ts. Depois rode o Expo em outra janela.

6. Banco de dados PostgreSQL

Configuração TypeORM

O backend configura TypeORM em backend/src/app.module.ts com synchronize: true. Em desenvolvimento, isso cria e ajusta tabelas automaticamente a partir das entidades. 

TypeOrmModule.forRoot({
  type: 'postgres',
  host: process.env.DB_HOST || 'localhost',
  port: parseInt(process.env.DB_PORT || '5432'),
  username: process.env.DB_USERNAME || 'postgres',
  password: process.env.DB_PASSWORD || '0000',
  database: process.env.DB_DATABASE || 'torresburgers',
  entities: [User, Product, Order, OrderItem, Address, Addon, StoreConfig],
  synchronize: true,
})
Importante: synchronize: true é conveniente em desenvolvimento, mas não deve ser usado em produção. Para produção, crie migrations TypeORM e desative o synchronize.

Criar banco limpo

createdb -U postgres torresburgers

Depois, inicie o backend. Ele criará as tabelas e a configuração inicial da loja em store_config com id=1 e is_open=true.

Restaurar backup SQL

O IDE indicava um arquivo chamado bdtorresburgers.backup.sql, mas esse arquivo não estava presente no filesystem no momento em que este guia foi gerado. Se o backup for entregue junto do projeto, use: 

createdb -U postgres torresburgers
psql -U postgres -d torresburgers -f bdtorresburgers.backup.sql

Se o dump tiver comandos de owner/role incompatíveis, edite o SQL ou restaure com um usuário compatível. Como o projeto usa synchronize: true, o backend pode completar colunas ausentes ao iniciar, mas isso não substitui migrations.

10. Autenticação, perfis e permissões

Roles

Role Uso esperado
CLIENTCliente que faz pedidos e gerencia seus endereços.
ADMINAcesso total administrativo.
KITCHENOperação de pedidos/cozinha.
COURIEREntregador/motoboy.
EMPLOYEEFuncionário genérico com acesso parcial no web.

Login

POST /auth/login recebe email e password. Resposta:

{
  "access_token": "jwt...",
  "user": {
    "id": 1,
    "name": "Admin Torres",
    "email": "admin@torresburgers.com",
    "role": "ADMIN"
  }
}

Senha

A senha deve ter no mínimo 9 caracteres, pelo menos uma letra maiúscula e um número ou símbolo. As senhas são salvas com Bcrypt usando saltRounds = 10.

Segurança de bootstrap: POST /users está público e aceita role. Isso facilita criar o primeiro admin, mas em produção deve ser protegido ou separado em um fluxo de seed controlado.

14. Fluxos principais

Cadastro e login

  1. Cliente ou admin cria usuário via POST /users.
  2. Senha é validada pelo DTO e salva como password_hash com Bcrypt.
  3. Login via POST /auth/login.
  4. Frontend salva token e usuário em storage local.
  5. Axios envia o token como bearer nas próximas requisições.

Pedido delivery

  1. Cliente consulta /store/status e /products.
  2. Cliente monta carrinho com produtos, adicionais, ponto da carne, observações e remoções de ingredientes.
  3. Cliente escolhe ou cria endereço em /addresses.
  4. Checkout pode passar por /payment/pix ou /payment/card.
  5. Cliente cria pedido em POST /orders com role CLIENT.
  6. Backend calcula frete por bairro e tempo estimado.
  7. Equipe acompanha e muda status no painel.

Pedido retirada

Para TAKEOUT, addressId não é obrigatório, o frete é 0 e o tempo estimado é 15-20 min.

Logística de entregas

  1. ADMIN lista motoboys em GET /orders/drivers/list.
  2. ADMIN atribui motoboy com PATCH /orders/:id/assign.
  3. O pedido vai automaticamente para DELIVERING.
  4. GET /orders/:id/nearby sugere pedidos READY_FOR_PICKUP do mesmo bairro e sem driver.

Pagamento

O Mercado Pago está em modo sandbox. O backend possui fallback e simulação: cartão rejeitado ou erro técnico pode retornar status aprovado simulado; PIX pode retornar um QR visual mock se o sandbox falhar. Isso é útil para desenvolvimento, mas deve ser removido/isolado em produção.

15. Uploads e imagens

Uploads de usuários, produtos e upload avulso passam pelo OptimizeImagePipe. O pipe valida JPG/JPEG/PNG/WebP, cria a pasta uploads se necessário, redimensiona para largura máxima de 800px e converte para WebP com qualidade 80.

O backend expõe a pasta uploads em /uploads via ServeStaticModule. Produtos salvam apenas o nome do arquivo; avatares de usuário normalmente salvam /uploads/<arquivo>. 

POST /uploads
Content-Type: multipart/form-data
Campo do arquivo: file
Resposta: { "filename": "compressed-...webp" }

17. Problemas conhecidos e recomendações

  1. Hardcoded secrets: mover token Mercado Pago e public keys para variáveis de ambiente.
  2. Porta hardcoded: usar process.env.PORT || 3000 em backend/src/main.ts.
  3. Frontend web ignora VITE_API_URL: refatorar frontend-web/src/services/api.ts para usar env.
  4. Mobile altera código ao rodar tunnel: considerar usar arquivo de ambiente ou Expo Constants.
  5. synchronize: true: trocar por migrations antes de produção.
  6. Rotas públicas sensíveis: proteger /addons, /uploads e /payment conforme necessidade.
  7. Criação pública de admin: após bootstrap, proteger criação de roles administrativas.
  8. CORS aberto: hoje origin: true. Em produção, restringir domínios.
  9. Payment sandbox bypass: não usar em produção.
  10. Sem Docker: criar docker-compose.yml para PostgreSQL e, se desejado, API.
  11. Sem .env.example: criar exemplos para backend, web e mobile.
  12. Lint web falhando: decidir se as regras são desejadas ou ajustar/refatorar gradualmente.
  13. Backup SQL ausente no filesystem atual: se o projeto depende de dados iniciais, versionar um seed seguro ou entregar dump sanitizado.

18. Troubleshooting

Backend não conecta no banco

  • Confirme que PostgreSQL está rodando: systemctl status postgresql.
  • Confirme que o banco existe: psql -U postgres -l.
  • Confira DB_HOST, DB_PORT, DB_USERNAME, DB_PASSWORD e DB_DATABASE.

Web não acessa API

  • Verifique se a API está em http://localhost:3000.
  • Confira frontend-web/src/services/api.ts.
  • Abra http://localhost:3000/api para validar que o backend está vivo.

Mobile não acessa API

  • Rode o backend antes de abrir o túnel.
  • Execute npm run tunnel em frontend-mobile.
  • Confirme que src/services/api.ts recebeu a nova URL pública.
  • Se Serveo cair, reinicie o túnel e o app Expo.

Pedido retorna "loja fechada"

  • Consulte GET /store/status.
  • Altere com ADMIN: PATCH /store/status enviando { "is_open": true }.

Erro ao criar pedido delivery

  • O usuário precisa ter role CLIENT.
  • Pedidos DELIVERY exigem addressId.
  • A loja precisa estar aberta.
  • Produtos precisam existir no banco.

Upload falha

  • Use campo multipart chamado file.
  • Use JPG, JPEG, PNG ou WebP.
  • Verifique permissão de escrita em backend/uploads.

Build web reclama do Node

Instale Node 20.19+ ou 22.12+ para alinhar com Vite 7.
