1. Visão geral

A Comestra é uma plataforma SaaS multi-tenant de delivery e gestão para restaurantes. Uma única instalação atende muitos estabelecimentos: cada loja tem equipe, cardápio, pedidos, pagamentos, configurações de entrega, identidade visual e assinatura próprios, isolados no servidor. A Comestra (dona da plataforma) administra tudo pelo superpainel. Os clientes têm conta global e compram em qualquer loja.

As permissões são aplicadas pela API (guards de loja, de perfil e da plataforma), e não apenas escondidas nas telas. A loja da equipe vem do usuário autenticado e a da vitrine vem do slug da rota: nenhum identificador de loja enviado pelo navegador concede acesso. Pagamentos do delivery (cliente → loja) e cobrança da assinatura SaaS (loja → Comestra) usam fluxos, tabelas, credenciais e webhooks separados.

2. Checklist de execução rápida

Caminho curto para subir tudo localmente, do zero. Os comandos valem para Linux e para o PowerShell do Windows, exceto onde indicado.

Atalho com Docker. Com Docker Desktop (ou Docker Engine com Compose v2): cp .env.docker.example .env.docker, preencha POSTGRES_PASSWORD, JWT_SECRET e CREDENTIALS_ENCRYPTION_KEY (os comandos de geração estão no arquivo) e rode docker compose up -d --build. O site abre em http://localhost:8080 (API em /api), no modo demonstração. Guia completo: docs/saas/docker.md. Os passos abaixo são a instalação sem Docker.

1. Clonar o projeto e criar o banco

git clone <URL_DO_REPOSITORIO> comestra
cd comestra

# Windows (PowerShell) — troque 18 pela versão instalada do PostgreSQL
& "C:\Program Files\PostgreSQL\18\bin\createdb.exe" -U postgres comestra
# Linux
sudo -u postgres createdb comestra

2. Configurar e subir a API

cd backend
cp .env.example .env        # Windows: Copy-Item .env.example .env
# edite o .env: NODE_ENV=development e DB_PASSWORD (deixe DB_SYNCHRONIZE vazio = false)
npm install
npm run start:dev

A API aplica as 14 migrations e cria a loja Lanchonete Demo (/loja/demo, loja padrão, aberta) com a equipe demo e um cliente demo. Confira: http://localhost:3000/health responde {"status":"ok"}, o log mostra API Comestra escutando em 0.0.0.0:3000 (todas as interfaces: acessível pela rede local) e o Swagger fica em http://localhost:3000/api. Sem JWT_SECRET, a primeira subida em development cria um segredo aleatório desta máquina em backend/.temp/dev-jwt-secret (fora do Git).

3. Criar o seu superadmin

npm run platform:superadmin -- --email=voce@exemplo.com --name="Seu Nome"   # a senha aparece uma única vez

4. Subir o site, os painéis e o superpainel

cd ../frontend-web
npm install
npm run dev

Diretório em http://localhost:5173, vitrine demo em /loja/demo, login do cliente em /signin, equipe e superadmin em /login (o superadmin vai para /platform).

6. Criar uma segunda loja

No superpainel: Lojas → Nova loja. A loja nasce fechada, com a entrega desligada, a assinatura do plano escolhido e um convite do responsável (o link aparece uma vez; com SMTP, também vai por e-mail). Abra o link em /convite/:token, defina a senha, configure a loja, cadastre o cardápio e abra a loja.

6. Banco de dados e migrations

O schema vem das migrations TypeORM em backend/src/database/migrations (registradas em index.ts), aplicadas na subida da API (DB_MIGRATIONS_RUN) ou pelos comandos abaixo. Cada migration roda na própria transação, exceto a PerformanceIndexes (índices com CONCURRENTLY).

MigrationO que faz
1791764966404-BaselineSchemaSchema exato da versão de loja única. Num banco existente não faz nada. Irreversível.
1791765597480-MultiTenantFoundationTabelas da plataforma; store_id nas tabelas operacionais; migração dos dados para a loja inicial; FKs, índices, CHECKs e triggers.
1791773437187-TenancyIndexesÍndices por loja/cliente e únicos parciais (convite pendente por loja + e-mail; fatura por período). Idempotente (IF NOT EXISTS).

Atualizar uma instalação existente

  1. Backup do banco (pg_dump, sempre antes de migrations novas) e das imagens.
  2. DB_SYNCHRONIZE=false (ou vazio) no backend/.env.
  3. Vindo de uma versão sem as sessões registradas (AuthSessions): defina JWT_LEGACY_ISSUED_BEFORE com o instante do deploy (ex.: 2026-11-01T12:00:00Z) para os tokens antigos valerem até expirar; sem ela, em produção, todos (site, app mobile e equipe) entram de novo.
  4. Atualize o código e rode npm install em backend/ e frontend-web/.
  5. Suba a API (as pendentes são aplicadas na subida) ou rode npm run migration:run; confira com migration:show (13 com [X]) e migration:check. Quem já tinha as 7 primeiras recebe 6 novas, todas aditivas.
  6. Se havia credenciais Mercado Pago gravadas, rode Regravar credenciais em Superpainel → Configurações → Manutenção (formato antigo → atual).
O número do pedido muda nas telas. A OrderNumbersAndCustomerBlocks renumera os pedidos existentes por loja (1, 2, 3... em cada loja, na ordem de criação). Antes, as telas mostravam Pedido #<id>, o id global: o pedido que era "Pedido #1532" pode virar "Pedido #87". Conversas, comprovantes e anotações antigas que citavam o id deixam de bater com o número exibido; avise as lojas antes de atualizar. O id não muda: continua nas rotas da API, nos pagamentos e no app mobile.

A PlatformIntegrity recusa subir se alguma conta com papel global também for da equipe de uma loja: a mensagem lista as contas; remova o papel (npm run platform:superadmin -- --email=<e-mail> --revoke) ou tire a conta da equipe e rode de novo. Uma migration que falha é desfeita e a API não sobe; as anteriores continuam aplicadas (a PerformanceIndexes, fora de transação, completa os índices que faltam na próxima execução).

Da loja única para o SaaS

  1. Opcional: INITIAL_STORE_NAME="Minha Lanchonete" e INITIAL_STORE_SLUG=minha-lanchonete.
  2. A MultiTenantFoundation cria a loja inicial com o status e as mensagens de store_config, associa a ela cardápio, pedidos, pagamentos e a equipe (clientes continuam globais), cria o plano interno legado (sem cobrança e sem limites) com uma assinatura ativa, grava o retrato do endereço nos pedidos de entrega antigos e define a loja inicial como loja padrão.
  3. Crie o superadmin e revise a loja: nome, endereço, telefone, horários, fuso, zonas e taxas de entrega, prazo de retirada, credenciais Mercado Pago, logo e cor. Produtos sem adicionais marcados deixaram de aceitar adicionais.

Reverter

Prefira restaurar o backup e reverta sempre junto com o código anterior. DeliveryDistance apaga o local das lojas e as coordenadas dos endereços (antes, volte as lojas que cobram por distância para o modo por zonas); AuthSessionRefresh tira o refresh das sessões em cookie (quem estava nelas entra de novo); AccountEmailVerification perde as confirmações e os links pendentes; PerformanceIndexes remove os índices (não a extensão); StoreSlugHistoryAndCancelOrigin perde a origem dos agendamentos e as reservas de slug; PlanStorageLimit e AddressZoneLocation removem as colunas; AuthSessions encerra as sessões de todas as contas e apaga a tabela de sessões; OrderNumbersAndCustomerBlocks remove os números dos pedidos e os bloqueios de clientes (que ficam só na auditoria; com bloqueios gravados, exige DB_ALLOW_DESTRUCTIVE_REVERT=true); PlatformIntegrity perde a origem das suspensões; MaintenanceJobs apaga o histórico da manutenção; TenancyIndexes remove os índices; MultiTenantFoundation só reverte com uma loja e recusa se for apagar auditoria, cobrança SaaS, sessões de suporte, convites ou redefinições, ou desfazer bloqueios e revogações de sessão, salvo com DB_ALLOW_DESTRUCTIVE_REVERT=true; BaselineSchema é irreversível.

10. Planos e assinaturas

TRIALING  → ACTIVE | PAST_DUE | CANCELED
ACTIVE    → PAST_DUE | SUSPENDED | CANCELED
PAST_DUE  → ACTIVE | SUSPENDED | CANCELED
SUSPENDED → ACTIVE | CANCELED
CANCELED  → (final; nova contratação cria outra assinatura)
  • Rotina (a cada SAAS_BILLING_INTERVAL_MS): fim do teste → ACTIVE (plano gratuito) ou fatura + PAST_DUE; fim do período → renovação (fatura) ou CANCELED (cancelamento agendado); fim da tolerância → SUSPENDED com suspended_by = BILLING.
  • Pagamento (manual ou webhook validado) → fatura PAID + ACTIVE com período novo. Notificações repetidas não duplicam efeitos.
  • Suspensão pela plataforma (PLATFORM): o pagamento quita a fatura mas não reativa; só a reativação pelo superadmin devolve a loja. O checkout da loja responde 409 e a página Assinatura mostra o aviso, sem o botão de pagamento.
  • Limites: equipe ativa e produtos fora da lixeira (rígidos: trava por loja, inclusive na restauração e no aceite de convite), pedidos do mês (calendário da loja; conta também os pagamentos aprovados sem pedido, os cartões em análise e os PIX pendentes do próprio cliente) e armazenamento (imagens da loja, conferido antes de gravar: 403 com o aviso do plano; avatares não contam). Downgrade só se o uso couber. Recursos: pagamentos online, relatórios avançados, identidade visual.
  • Quem agendou o cancelamento (cancel_scheduled_by): se foi a plataforma, a loja não desfaz (vê "fale com o suporte"). O cancelamento imediato pela loja (sem período pago a terminar) fica só com o responsável.
  • Troca de plano vale na hora, sem proporcionalidade. Cancelamento imediato anula só faturas de períodos futuros. Uma fatura válida por período. monthly_price é arredondado em centavos.
  • Provedores: MANUAL (faturas registradas pelo superadmin; o webhook SaaS sem token responde 200 e registra IGNORED) e MERCADO_PAGO (preapproval na conta da Comestra; implementado, ainda não validado contra o Mercado Pago real). Com o Mercado Pago: cobrança depois do cancelamento tenta cancelar a autorização de novo; preapproval órfã é cancelada; a rotina repete o cancelamento no provedor com intervalo crescente; o checkout é serializado por loja (409 se outro checkout da loja demorar; limite SUBSCRIPTION_CHECKOUT).

Preço calculado no servidor

  • O cliente nunca envia preços. Promoção só quando menor que o preço normal; cálculos em centavos; addonIds repetidos indicam a quantidade.
  • Só adicionais permitidos no produto; produto sem adicionais configurados não aceita nenhum (400). Produto ou adicional indisponível, na lixeira ou de outra loja → "não encontrado", sem revelar o nome.

  • Retrato do preço (unit_price, addons_snapshot) e do endereço: o histórico não muda quando o cardápio ou o endereço mudam.
  • Abuso: ORDER_CREATE (cliente + loja) e ORDER_CREATE_IP; no máximo N pedidos pagos na entrega aguardando a loja por cliente (N = limite de ORDER_CREATE, padrão 10) → 429.
  • Entrega: a loja padrão usa as zonas da plataforma (DELIVERY_ZONES_*); as demais usam as zonas configuradas no painel e, sem elas, não entregam. Vale a primeira zona com o bairro do CEP (conferido pela API; sem o serviço, o digitado) ou com o CEP numa faixa. Fora das zonas: taxa padrão (fallback) ou recusa (refuse → 400 DELIVERY_OUT_OF_AREA no orçamento, no pedido e nas cobranças, antes de cobrar; pagamento já aprovado nunca é recusado). Retirada é grátis. Pedido mínimo, frete grátis e cobrança por distância: subseção "Entrega" abaixo.
  • Número do pedido: toda resposta de pedido traz number, o número do pedido na loja (1..N, sem buraco nem repetição, inclusive com pedidos simultâneos), atribuído pelo banco em todo pedido novo e imutável. As telas mostram Pedido #<number>; o id continua sendo a chave das rotas e do app mobile. number no corpo do pedido → 400.
  • Cliente bloqueado pela loja: 403 no orçamento, no pedido pago na entrega e nas cobranças PIX/cartão daquela loja (rotas por slug e antigas). Não afeta outras lojas nem um pagamento já aprovado, que continua virando pedido.

14. Pagamentos do delivery

Por loja

  • Cada loja informa a própria conta Mercado Pago em Configurações (token cifrado com CREDENTIALS_ENCRYPTION_KEY, vinculado à loja, nunca devolvido). O MP_ACCESS_TOKEN do ambiente vale só para a loja padrão sem credencial própria. Loja sem credencial: só pagamento na entrega.
  • A chave pública da loja sai no perfil público (tokenização no navegador). Idempotência e estorno por loja.

Fluxo

  1. O front envia o pedido e uma idempotencyKey para /stores/:slug/payment/card ou /pix. A API calcula o valor, grava o pagamento (payments, com o retrato do carrinho) e cobra.
  2. Aprovado o pagamento (resposta do cartão, GET /payment/status/:id, webhook ou conciliação a cada 60 s), a própria API cria o pedido, uma única vez.
  3. Se a loja não puder mais vender (suspensa, desativada, assinatura suspensa/cancelada ou ausente), o pedido não é criado: o valor é estornado e o caso fica na auditoria. Loja apenas fechada continua recebendo o pedido.
  • Limites: PAYMENT_CREATE (cliente + loja) e PAYMENT_CREATE_IP; até 5 cobranças pendentes por cliente e loja; o mesmo carrinho com um PIX pendente devolve o mesmo PIX.
  • Entrega nas cobranças: PIX e cartão abaixo do pedido mínimo → 400 ORDER_BELOW_MINIMUM antes de cobrar (o mesmo do pedido pago na entrega); endereço fora da área ou não localizado numa loja que recusa → 400 DELIVERY_OUT_OF_AREA. Com frete grátis, o valor cobrado já sai sem a taxa. A recuperação de um pagamento aprovado nunca é recusada por essas regras.
  • Webhook (POST /payment/webhook): corpo não confiável, reconsulta no Mercado Pago no máximo a cada 15 s por pagamento, limite por IP e fila limitada.
  • Conciliação: 50 pagamentos por rodada, no máximo 10 por loja, aprovados sem pedido primeiro; cancela os pendentes de lojas que não vendem.
  • GET /payment/status/:id: o pagador ou ADMIN/EMPLOYEE da loja do pagamento; consulta o Mercado Pago no máximo a cada 5 s por pagamento.
  • Estorno ou contestação feitos no Mercado Pago depois da aprovação (com MP_NOTIFICATION_URL): o webhook reconsulta também os pagamentos aprovados, o pedido fica com payment_status = REFUNDED e a auditoria registra payment.reversed; o quadro avisa a equipe.
  • Com várias instâncias, a criação do pedido de um pagamento aprovado usa uma trava do banco por pagamento: o pedido nunca nasce enquanto outra instância estorna.

15. Segurança

Sessões e contas

  • JWT com versão de sessão (token_version): trocar ou redefinir a senha, confirmar ou desfazer uma troca de e-mail, bloquear, "encerrar sessões", desativar a loja (equipe) e promover pelo comando invalidam os tokens antigos.
  • Sessões registradas: todo token emitido pela API leva jti e ganha uma linha em auth_sessions, gravada antes de a resposta sair (se a gravação falhar, a resposta é 500 e nenhum token sai). Token com jti só vale com a sessão existente, não revogada e no prazo; token antigo sem jti só vale na janela de JWT_LEGACY_ISSUED_BEFORE (em produção, sem ela, é recusado). No máximo 100 sessões ativas por conta (as mais antigas caem). Sair (POST /auth/logout) encerra a sessão no servidor; "Sessões ativas" lista os aparelhos e encerra um ou todos (POST /auth/logout-all). Sessões mortas são apagadas a cada sessão nova da conta e, no máximo uma vez por hora por instância, em lotes de 5000 vencidas.
  • Sessão do site em cookie: com o cabeçalho X-Auth-Transport: cookie (só o site envia), o login devolve um token de 15 min, guardado só na memória da aba, e grava um refresh rotativo num cookie HttpOnly, SameSite=Strict (__Host-comestra_rt em produção ou HTTPS; comestra_rt em http fora de produção). POST /auth/web/refresh renova (o refresh anterior ainda vale por AUTH_REFRESH_GRACE_SECONDS; reuso fora disso encerra a sessão inteira e é auditado como auth.refresh.reuse); POST /auth/web/logout encerra. Um login novo no mesmo navegador encerra a sessão anterior no servidor. O app mobile não envia o cabeçalho e não muda. Kill switches: AUTH_WEB_COOKIE=false (API) e VITE_AUTH_TRANSPORT=bearer (build).
  • Conta bloqueada não entra. Recuperação de senha por link de uso único (hash no banco; no máximo 3 por conta em 24 h): com MAIL_DRIVER=smtp o link vai por e-mail; com o driver de log, o superadmin gera o link (com SMTP, o link do superpainel vai só ao dono). Links pendentes deixam de valer quando a conta troca e-mail ou senha, é bloqueada, vai para a lixeira, encerra as sessões ou a loja da equipe é desativada.
  • Minha conta (modo compat): troca de e-mail só depois da confirmação no endereço novo (resposta igual para endereço livre, em uso ou reservado); o endereço antigo recebe "Não fui eu", que por 7 dias desfaz a troca com uma senha nova, e fica reservado nesse período; troca de senha com a senha atual, com aviso ao dono. A rota antiga do app (PATCH /users/:id) continua trocando o e-mail na hora.
  • Em development sem JWT_SECRET, o segredo dos tokens é aleatório por instalação (backend/.temp/dev-jwt-secret), não mais derivado do nome da marca.
  • Sessão de suporte: qualquer POST, PUT, PATCH ou DELETE com o token de suporte → 403 "Sessão de suporte é somente leitura: nenhuma alteração pode ser feita." Única exceção: POST /auth/logout, que encerra a sessão de suporte com o próprio token (auditado).
  • Senha atual (current_password) obrigatória para contas da plataforma ao trocar e-mail ou senha e em Minha conta; opcional na rota antiga enquanto o app mobile não a envia. A regra de senha é validada em tempo linear (sem ReDoS), com as mesmas mensagens.
  • Avatar em texto só dos ícones prontos; fotos enviadas levam o dono no nome e a anterior é apagada.

Cabeçalhos HTTP da API

Sem X-Powered-By. Em toda resposta: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer, Cross-Origin-Resource-Policy: cross-origin e HSTS em produção. CSP: default-src 'none'; frame-ancestors 'none' na API; em /uploads, também style-src 'unsafe-inline' e sandbox; no Swagger, só frame-ancestors 'none'. Respostas comprimidas (gzip/br) acima de 1 KB; corpo JSON acima de 100 KB → 413 (2 MB em /store/settings). CORS com credenciais só para as origens do site (AUTH_COOKIE_ORIGINS ou CORS_ORIGINS + APP_WEB_URL).

SPA (frontend web)

  • O build de produção injeta a Content-Security-Policy por <meta> (origem de VITE_API_URL, Mercado Pago, Iconify, o host dos avatares e, só em img-src, https://tile.openstreetmap.org para as imagens do mapa do local da loja; o Leaflet vem no bundle). O Vite de desenvolvimento não tem CSP.
  • O servidor que hospeda o build deve enviar os cabeçalhos de securityHeaders() (vite.config.ts): CSP com frame-ancestors 'none', X-Frame-Options: DENY, nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy e HSTS em HTTPS.
  • Sessão por aba, sincronizada entre abas (login, saída, troca de conta, suporte); chamadas da sessão anterior são canceladas. No modo cookie, o token fica só na memória e o localStorage guarda só o marcador comestra.session (sem segredo); cada aba renova o próprio token (na subida, a 80% da validade, antes de chamadas e depois de um 401), com Web Lock entre abas. Sair apaga os carrinhos e a última loja (o tema fica) e chama POST /auth/logout (e /auth/web/logout) como melhor esforço, sem travar a saída.
  • Suporte iniciado numa sessão em cookie: nada do superpainel fica na aba; encerrar o suporte volta ao superpainel pelo refresh, mesmo depois de recarregar. Numa sessão bearer antiga, o token do superpainel fica só na memória da aba que o iniciou. "Encerrar e voltar ao superpainel" e "Sair do Sistema" encerram o suporte com o próprio token de suporte, na hora, mesmo depois de recarregar a página.
  • Com a CSP, o script antifraude do Mercado Pago só roda com um nonce gerado pelo servidor (o pagamento com cartão funciona sem ele).

Auditoria

Ator, escopo, loja, ação, alvo, resultado, IP, navegador e metadados sem senhas, tokens nem segredos: ações do superpainel, autenticação (inclusive auth.logout e auth.session.revoke), equipe e convites, configurações e credenciais, assinaturas, sessões de suporte (com via quando encerradas pelo próprio token), bloqueio e desbloqueio de clientes (store.customer.block/unblock), e-mail de teste, limpeza de arquivos (manual ou agendada, como sistema) e regravação de credenciais (só contagens), pagamentos que não viram pedido ou estornados no Mercado Pago (payment.reversed), os 409 de e-mail em uso, troca e confirmação de e-mail (auth.email_change.*, auth.email_verification.*), reuso de sessão (auth.refresh.reuse) e as leituras de dados pessoais no superpainel (platform.users.list/view, platform.store.team.view).

25. Troubleshooting

A API não conecta no banco

  • Confirme que o PostgreSQL está rodando (Windows: serviço postgresql-x64-<versão>; Linux: systemctl status postgresql) e que o banco existe (psql -U postgres -l).
  • Revise DB_HOST, DB_PORT, DB_USERNAME, DB_PASSWORD e DB_DATABASE. No Linux a conexão é TCP: o usuário precisa de senha (ou de trust no pg_hba.conf).

A API não sobe

  • "JWT_SECRET não definido...": defina um JWT_SECRET de 32+ caracteres (obrigatório em produção).
  • "Migration recusada: ... com papel global (platform_role) também pertence(m) à equipe...": remova o papel global (--revoke) ou tire a conta da equipe e suba de novo.
  • Migration de loja única recusada com a lista de colunas faltando: banco de uma versão muito antiga; suba uma vez a versão anterior com DB_SYNCHRONIZE=true (com backup) e rode as migrations de novo.
  • "A API não conseguiu escutar em <host>:<porta> (EADDRINUSE / EADDRNOTAVAIL...)": porta ocupada ou HOST que não existe nesta máquina. Confira HOST e PORT (um shell pode exportar HOST com o nome da máquina).

Contas e acesso

  • Contas demo não entram: cd backend && npm run seed (só dev/test) e confira se SEED_DEMO_USERS não está false.
  • Superadmin sem acesso: npm run platform:superadmin -- --email=<e-mail> --reset-password.
  • "Esta loja foi desativada na plataforma.": a equipe de loja desativada não entra; restaure a loja no superpainel.
  • "Sessão de suporte é somente leitura...": o token de suporte não altera nada; encerre o suporte e use uma conta da loja.
  • "A sessão mudou em outra aba...": outra aba trocou de conta ou saiu; a aba atual acompanha a sessão do navegador.
  • Todos precisaram entrar de novo depois de atualizar: os tokens antigos (sem jti) são recusados em produção sem JWT_LEGACY_ISSUED_BEFORE (defina-o com o instante do deploy na próxima vez). Em development, sem JWT_SECRET, o segredo passou a ser aleatório por máquina: entre de novo uma vez.
  • Ao recarregar a página do site, a sessão some: confira se o login trouxe o cookie (comestra_rt ou __Host-comestra_rt) e se POST /auth/web/refresh responde 200; em produção o site precisa de HTTPS e estar no mesmo site da API (CORS_ORIGINS/APP_WEB_URL exatos). Fora disso, o site usa o modo bearer, que também funciona.
  • "Sessão inválida ou expirada. Faça login novamente.": a sessão foi encerrada (sair, "Sessões ativas", "Sair de todos os aparelhos", superpainel, teto de 100 sessões, reuso de refresh) ou venceu. "A sessão de suporte terminou ou expirou...": inicie outra pelo superpainel.
  • Login responde 500 de vez em quando: a sessão não pôde ser gravada (banco indisponível); nenhum token foi entregue, tente de novo.
  • Convite, link de redefinição ou confirmação de e-mail não chegou: confira o driver em Superpainel → Configurações → E-mail transacional e envie um e-mail de teste; com o driver de log nada é enviado (copie o link exibido no painel). Confira também os limites: 3 links de "esqueci a senha" por conta em 24 h, 3 e-mails de conta por hora por destinatário e, nos convites, 10 por destinatário em 24 h somando as lojas (acima disso o convite sai sem e-mail).
  • Endereço recusado com "Este endereço está fora da área de entrega da loja.": a loja recusa endereços fora das zonas; o bairro usado é o do CEP. Revise as zonas (nomes dos Correios ou faixas de CEP) ou escolha a retirada.

A web não acessa a API

  • Abra http://localhost:3000/health, confira VITE_API_URL e reinicie o npm run dev depois de mudá-la.
  • Com CORS_ORIGINS preenchido, inclua a origem do site.
  • No build de produção, chamadas bloqueadas pela CSP indicam um build gerado com outra VITE_API_URL: gere o build de novo com a URL real.

Pedido recusado

  • "A loja está fechada no momento.": abra a loja no painel (Dashboard ou Pedidos).
  • "Esta loja está temporariamente indisponível para novos pedidos.": a loja está suspensa ou a assinatura não permite vender; veja o motivo no painel da loja ou no superpainel.
  • "O produto "X" não aceita adicionais.": marque os adicionais permitidos no cadastro do produto.
  • "Valor para troco acima do permitido...": informe até R$ 200 acima do total.
  • "O pedido mínimo desta loja para entrega é R$ X. Faltam R$ Y." (400 ORDER_BELOW_MINIMUM): o total dos produtos (sem a taxa) está abaixo do mínimo da loja ou da zona/faixa do endereço. Confira em Configurações → Entrega.
  • "Este endereço está fora da área de entrega da loja." ou "Não conseguimos localizar este endereço no mapa...": a loja recusa endereços fora da área (ou além do raio, no modo distância). No segundo caso, confira CEP, rua e número; com os serviços de mapa fora do ar, a API tenta de novo depois de 1 h. Em produção, confira GEOCODING_CONTACT, GEOCODING_PROVIDERS e a saída da API para a internet.
  • Loja não salva o modo distância ("Para cobrar a entrega por distância, informe o local da loja no mapa..."): use "Localizar pelo endereço da loja" ou marque o ponto no mapa antes de salvar.
  • 429 em pedidos, pagamentos ou endereços: limite de abuso; atrás de proxy, configure TRUST_PROXY para os limites por IP não juntarem todos os clientes.
  • "Contas da administração da plataforma não fazem pedidos..." ou "Somente clientes fazem pedidos...": entre com uma conta de cliente.
  • "Não é possível fazer pedidos nesta loja. Fale com a loja.": o cliente foi bloqueado por essa loja (Painel → Clientes → filtro Bloqueados); só o administrador da loja desbloqueia.
  • Pedido recusado por chave duplicada em UQ_orders_store_number depois de restaurar ou importar pedidos: o contador da loja ficou para trás. Corrija com o SQL de docs/saas/operacao.md (seção 8.3), que leva store_order_counters ao maior número de cada loja.

Pagamento online

  • 503 "Esta loja ainda não aceita pagamento online...": a loja não tem credenciais Mercado Pago utilizáveis (Configurações → Pagamentos) ou, em produção, CREDENTIALS_ENCRYPTION_KEY não está definida ou é inválida. O pagamento na entrega continua funcionando.
  • "Você já tem pagamentos pendentes nesta loja...": pague ou cancele um PIX pendente.
  • "Pagamento não encontrado ou expirado...": o paymentId não existe, venceu ou é de outro cliente ou loja.
  • Cartão não carrega na web: o SDK do Mercado Pago precisa de internet e não é carregado para contas da equipe ou da plataforma.

Upload falha

  • Um único arquivo no campo file, JPG, PNG ou WebP de até 5 MB e até 40 megapixels.
  • 429: limite de uploads por conta (multipart malformado também conta). Verifique também a permissão de escrita em UPLOADS_DIR.
  • 403 "Limite de armazenamento do plano ... atingido": a loja chegou ao max_storage_mb do plano. Aumente o limite ou troque o plano no superpainel, ou rode a limpeza dos arquivos sem uso.
  • 400 "Formulário inválido: nome de campo não aceito.": nome de campo multipart aninhado demais ou com índice acima de 300.

Testes E2E não sobem

  • Informe DB_PASSWORD no ambiente (o reset do banco não lê o backend/.env) e confira se o Google Chrome está instalado.
  • Portas 3001/5174 ocupadas: libere-as ou use E2E_API_PORT/E2E_WEB_PORT. Mudou o backend? Pare a API de teste para o npm test recompilar. Compilar de novo numa pasta dist-e2e-* própria falha com TS5055: apague a pasta antes.

Docker

  • dependency failed to start: container comestra-api-1 is unhealthy: veja docker compose logs api (JWT_SECRET vazio ou curto em produção, senha do banco diferente da gravada no volume ou migration com erro).
  • Porta 8080 ocupada: COMESTRA_HTTP_PORT=8081 docker compose up -d e ajuste APP_WEB_URL, CORS_ORIGINS e PUBLIC_API_URL. Outros casos em docs/saas/docker.md, seção 11.
