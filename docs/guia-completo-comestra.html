1. Visão geral

O Comestra é um SaaS de delivery e gestão para restaurantes. Ele cobre o pedido de ponta a ponta, do cardápio online até a entrega, com três aplicações ligadas a uma única API REST: a loja online e o back office (o mesmo app web, em React) e o app mobile (Expo), que serve tanto a clientes quanto à equipe. Cada instalação atende uma loja.

Camada Tecnologias Responsabilidade
API (backend/) NestJS 11, TypeScript, TypeORM 0.3, PostgreSQL, Passport JWT, bcrypt, class-validator, Swagger, Sharp, SDK do Mercado Pago Regras de negócio, autenticação e perfis, preço calculado no servidor, pagamentos, imagens e integrações externas.
Web (frontend-web/) React 19, Vite 7, TailwindCSS 4, React Router 7, Axios, Recharts, Lucide/Iconify, SDK JS v2 do Mercado Pago Loja (cardápio, carrinho, checkout, Meus Pedidos, Meus Dados) e back office (Dashboard, Pedidos, Cardápio, Equipe, Lixeira).
Mobile (frontend-mobile/) React Native 0.81, Expo SDK 54, NativeWind 2, React Navigation 7, Axios, AsyncStorage Loja do cliente e painel da equipe por perfil, no mesmo app.
Testes (e2e/) Playwright (API + Google Chrome) Testes ponta a ponta em ambiente isolado (API :3001, web :5174, banco comestra_e2e).

Perfis de acesso

PerfilResumo
ADMIN (Administrador)Acesso total: Dashboard, pedidos, cardápio, equipe, lixeira, loja aberta/fechada e manutenção.
EMPLOYEE (Atendente)Conduz todo o fluxo dos pedidos, despacha entregas, cancela e abre/fecha a loja. Não acessa financeiro, cardápio nem equipe.
KITCHEN (Cozinha)Inicia o preparo e marca o pedido como pronto.
COURIER (Entregador)Pega pedidos prontos para entrega e conclui as próprias entregas.
CLIENT (Cliente)Compra pela loja: carrinho, checkout, pagamentos, endereços e acompanhamento dos pedidos.
As permissões são aplicadas pela API (guards por perfil e regras de transição), e não apenas escondidas nas telas. A identidade do produto (nome, slug comestra, domínio comestra.com.br) fica em src/config/brand.ts de cada app.

2. Checklist de execução rápida

Caminho curto para subir tudo localmente. Os comandos de terminal valem para Linux e para o PowerShell do Windows, exceto onde indicado.

1. Clonar o projeto

git clone <URL_DO_REPOSITORIO> comestra
cd comestra

2. Criar o banco

# Windows (PowerShell) — troque 18 pela versão instalada do PostgreSQL
& "C:\Program Files\PostgreSQL\18\bin\createdb.exe" -U postgres comestra

# Linux
sudo -u postgres createdb comestra

3. Configurar e subir a API

cd backend
cp .env.example .env        # Windows: Copy-Item .env.example .env
# edite o .env: DB_PASSWORD = senha do usuário postgres
npm install
npm run start:dev

A API cria as tabelas, a configuração da loja (aberta) e os cinco usuários padrão. Para conferir: http://localhost:3000/health deve responder {"status":"ok","name":"Comestra","version":"0.0.1"}, e o Swagger fica em http://localhost:3000/api.

4. Subir a loja e o back office

cd ../frontend-web
npm install
npm run dev

Loja em http://localhost:5173, login do cliente em /signin e da equipe em /login.

5. Rodar o app mobile

cd ../frontend-mobile
npm install
npm run start:lan

Escaneie o QR Code com o Expo Go (SDK 54), com o celular no mesmo Wi-Fi do computador. Outras formas de conexão estão na seção 9.

6. Banco de dados PostgreSQL

Configuração TypeORM

A conexão é configurada em backend/src/app.module.ts:

TypeOrmModule.forRootAsync({
  useFactory: () => ({
    type: 'postgres',
    host: process.env.DB_HOST || 'localhost',
    port: Number(process.env.DB_PORT) || 5432,
    username: process.env.DB_USERNAME || 'postgres',
    password: process.env.DB_PASSWORD ?? '',
    database: process.env.DB_DATABASE || BRAND.slug,      // 'comestra'
    entities: [User, Product, Order, OrderItem, Address, Addon, StoreConfig],
    autoLoadEntities: true,
    synchronize: envFlag('DB_SYNCHRONIZE', true),
  }),
})
Produção: o synchronize é prático em desenvolvimento, mas pode apagar colunas. Em produção, use DB_SYNCHRONIZE=false e versione o schema com migrations. O repositório ainda não traz migrations nem um data source para o CLI do TypeORM: crie-os antes da primeira subida em produção.

Criar um banco limpo

# Windows (PowerShell)
& "C:\Program Files\PostgreSQL\18\bin\createdb.exe" -U postgres comestra

# Linux (se o usuário postgres ainda não tiver senha, defina uma: a API conecta via TCP)
sudo -u postgres createdb comestra
sudo -u postgres psql -c "ALTER USER postgres PASSWORD 'sua_senha';"

Na primeira subida, a API cria as tabelas, a linha única de store_config (loja aberta) e os usuários padrão. O cardápio começa vazio.

Backup e restauração

pg_dump -U postgres -Fc comestra > comestra.dump        # backup
createdb -U postgres comestra_restaurado
pg_restore -U postgres -d comestra_restaurado comestra.dump   # restauração

Inclua também a pasta de imagens (UPLOADS_DIR) no backup.

Instalações antigas (TorresBurgers)

Para continuar usando o banco antigo, defina DB_DATABASE=torresburgers (e DB_PASSWORD=0000, se a instalação dependia da senha padrão do código antigo). Para copiar os dados para o nome novo: createdb -U postgres -T torresburgers comestra, sem conexões abertas no banco antigo. Com DB_SYNCHRONIZE=true, a API acrescenta as colunas novas, como o retrato de preços dos itens.

Comportamento global

  • Validação: ValidationPipe com whitelist, forbidNonWhitelisted (campos desconhecidos → 400) e transform. A mesma configuração (src/config/app-setup.ts) é usada nos testes.
  • CORS: CORS_ORIGINS vazio reflete qualquer origem (desenvolvimento). Com a lista preenchida, libera só essas origens.
  • JWT: segredo único para assinar e verificar (src/config/jwt.ts). Em produção sem JWT_SECRET, a API não sobe.
  • Usuário a cada requisição: a JwtStrategy recarrega o usuário do banco. Conta na lixeira → 401. O perfil usado é sempre o atual.
  • Subida: cria a configuração da loja (se não existir) e os usuários padrão (se SEED_DEMO_USERS). Uma falha no seed não derruba a API.

Como o app encontra a API

Ordem de prioridade (src/services/api.ts):

  1. EXPO_PUBLIC_API_URL (.env/.env.local), preenchida pelo npm run tunnel.
  2. O IP da máquina que roda o Expo (tirado do endereço do Metro), na porta 3000.
  3. http://localhost:3000 (navegador e simulador iOS).
SituaçãoComo fazer
Celular no mesmo Wi-Finpm run start:lan. Automático. Libere a porta 3000 no firewall. No Windows, como administrador: New-NetFirewallRule -DisplayName "Comestra API" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow. No Linux com ufw: sudo ufw allow 3000/tcp.
Emulador Androidnpm run android (o modo LAN funciona). Se necessário, use EXPO_PUBLIC_API_URL=http://10.0.2.2:3000 no .env.local, ou adb reverse tcp:3000 tcp:3000 com http://127.0.0.1:3000.
Rede corporativa, 4G ou celular fora da redeTerminal 1: npm run tunnel (deixe aberto). Terminal 2: npx expo start --clear (mesma rede) ou npx expo start --tunnel --clear (fora da rede). Ao encerrar o túnel (Ctrl+C), o .env.local volta ao valor anterior.
Com o Expo em --tunnel e sem EXPO_PUBLIC_API_URL, o app avisa no log ("Expo em modo túnel: defina EXPO_PUBLIC_API_URL") e cai em localhost, que não funciona no celular. Rode o npm run tunnel antes.

Navegação por perfil

  • Uma única pilha cujas telas dependem da sessão: a equipe vê só o painel (AdminDashboard), e clientes e visitantes veem a loja.
  • Visitante: na loja, toque em Entrar → Entrar como Cliente ou Acesso de Funcionário. O destino depende do perfil da conta.
  • Painel: Administrador com Dashboard, Pedidos, Produtos e Usuários. Atendente com Pedidos ("Gestão de Pedidos"). Cozinha com "Monitor da Cozinha" (Novos e Em preparo). Entregador com "Minhas Entregas" (Prontos para entrega e Minhas entregas, com Abrir no GPS e Ligar).
  • Telas da loja: Home, ProductDetails, Cart, Checkout, AddAddress, PaymentPix, PaymentCard, MyOrders, OrderDetails, Profile ("Minha Conta"), Welcome, SignIn, SignUp e ForgotPassword.

Sessão

O AsyncStorage guarda @comestra:token, @comestra:user e @comestra:themeMode. Um 401 encerra a sessão e abre o login certo, avisando que a sessão expirou. Sair remove só a sessão. O cartão é tokenizado direto na API REST do Mercado Pago com a chave pública: o número não passa pela API do Comestra.

CLIENTcliente@comestra.com.brCliente@123Comprar: carrinho, checkout, Meus Pedidos e dados da conta.
  • Na subida da API (SEED_DEMO_USERS, ligado fora de produção): cria só os que faltam e nunca altera contas existentes.
  • npm run seed (pasta backend): recria os que faltam, restaura da lixeira e redefine nome, perfil e senha. No fim, mostra uma tabela com perfil, e-mail e senha.
  • Fonte: backend/src/database/seeds/default-users.ts. Os e-mails usam BRAND.domain.
Produção: use SEED_DEMO_USERS=false (padrão com NODE_ENV=production). Essas senhas são públicas. Se as contas já existirem, exclua-as ou troque as senhas.

Regras de conta

  • Login (POST /auth/login): devolve { access_token, user }. O token traz sub, email, role e name e vale 7 dias por padrão.
  • E-mail gravado sem espaços e em minúsculas. O login não diferencia maiúsculas.
  • Senha: no mínimo 9 caracteres, com uma letra maiúscula e um número ou símbolo. É guardada com bcrypt (10 rounds) e nunca sai nas respostas.
  • Cadastro (POST /users): sem token, cria CLIENT. Outros perfis exigem token de ADMIN. Só o ADMIN altera o perfil de alguém.
  • Exclusão: a própria conta ou um ADMIN (que não exclui a si mesmo). A exclusão definitiva é só do ADMIN e é bloqueada (409) para contas com pedidos.
  • Recuperação de senha: não é automática. Um Administrador define uma nova senha (web: Equipe; app: Usuários → editar).
  • Compras: pedidos e pagamentos online são exclusivos de CLIENT. A equipe recebe 403 ("Somente clientes fazem pedidos e pagamentos...").

12. Pedidos: regras e transições

As regras ficam em funções puras em backend/src/orders/order-rules.ts, cobertas por testes unitários.

Preço calculado no servidor

POST /orders
{
  "type": "DELIVERY",
  "addressId": 3,
  "items": [
    { "productId": 1, "quantity": 2, "addonIds": [4, 4], "meatPoint": "Ao Ponto",
      "removedIngredients": ["Cebola"], "observation": "Capricha no molho" }
  ],
  "paymentMethod": "MONEY",
  "changeFor": "R$ 100,00"
}
  • O cliente nunca envia preços. O preço unitário é o promocional quando ele existe e é menor que o normal. Os cálculos são feitos em centavos.
  • addonIds repetidos indicam a quantidade ([4, 4] = 2×). Se o produto define adicionais permitidos, só eles são aceitos.
  • Produtos e adicionais indisponíveis ou na lixeira são recusados com a mensagem do motivo.
  • Limites: 50 linhas por pedido, 50 unidades por item, 50 adicionais por item e observação de até 300 caracteres.
  • DELIVERY exige um endereço ativo do próprio cliente ("Endereço obrigatório para delivery.").
  • Retrato do preço: cada item grava unit_price e addons_snapshot (nome, preço e quantidade cobrados). Pedidos antigos sem retrato continuam legíveis.
  • Loja fechada: o orçamento devolve store_open: false, e o pedido e os pagamentos respondem 400 ("A loja está fechada no momento.").

Entrega por bairro

Vale a primeira faixa cujo termo aparece no nome do bairro, sem diferenciar acentos e maiúsculas. Por exemplo, "Barra da Tijuca" entra na faixa da Barra.

Pagamento e troco

  • Formas: PIX, CREDIT_CARD, DEBIT_CARD e MONEY. Com paymentId, o pedido foi pago online. Sem ele, o pagamento é feito na entrega ou na retirada (cartão = maquininha).
  • O troco só vale para MONEY. É gravado como "R$ 50,00" e precisa ser maior ou igual ao total.
  • Ao concluir (DONE) um pedido pago na entrega ou na retirada, payment_status vira PAID.

Transições de status por perfil

AçãoGestãoCozinhaEntregador
Aceitar: PENDING → PREPARINGsimsim—
Pronto: PREPARING → READY_FOR_PICKUPsimsim—
Despachar com entregador escolhido (/assign)sim——
Pegar para entrega: READY_FOR_PICKUP → DELIVERINGsim—sim (assume se sem responsável)
Confirmar entrega: DELIVERING → DONEsim—só as próprias
Balcão (retirada): READY_FOR_PICKUP → DONEsim——
Cancelaraté concluir——
  • A gestão (ADMIN, EMPLOYEE) pode fazer qualquer transição válida. DONE e CANCELED são finais, o mesmo status é inválido e TAKEOUT nunca entra em DELIVERING.
  • Transição impossível → 400 "Transição inválida: X → Y". Transição possível, mas não permitida ao perfil → 403.
  • O cliente cancela o próprio pedido enquanto ele está PENDING (PATCH /orders/:id/cancel).
  • Despacho (/assign): só para DELIVERY em PREPARING, READY_FOR_PICKUP ou DELIVERING (troca de entregador), com um COURIER ativo.
  • Concorrência: a gravação só acontece se o pedido ainda estiver no status lido (e, ao assumir uma entrega, sem entregador). Caso contrário, a resposta é 409, e só um de dois entregadores simultâneos assume o pedido.
  • Dashboard: o faturamento conta apenas pedidos PAID e não cancelados.

PIX: gere o QR e aguarde cerca de 5 s. A web consulta o status a cada 3 s e o app a cada 4 s, e o pedido é registrado sozinho após a aprovação. O código PIX expira na tela depois de 10 minutos (é preciso gerar outro).

Fluxo e verificações

  1. O front envia order (o mesmo corpo do orçamento) para /payment/card (com o token do cartão, bandeira e CPF/CNPJ) ou /payment/pix. O valor é sempre calculado pela API.
  2. Com o pagamento aprovado, o front cria o pedido em POST /orders com paymentId e a forma de pagamento.
  3. Antes de gravar, a API confere: pagamento criado por ela para o mesmo cliente, forma compatível (PIX ↔ PIX, cartão ↔ crédito/débito), aprovado (pagamentos reais são consultados de novo no Mercado Pago), valor ≥ total − R$ 0,01 e não usado em outro pedido (payment_id único). Qualquer falha → 400, e nada é gravado.
  4. Se a criação do pedido falhar depois de um pagamento aprovado, a web guarda o pagamento na aba para tentar de novo sem cobrar outra vez.
Limitação atual: o registro dos pagamentos fica em memória na API (validade de 24 h). Um reinício entre o pagamento e a criação do pedido faz a criação falhar ("Pagamento não encontrado ou expirado..."), e o pagamento precisa ser conferido no painel do Mercado Pago. O webhook (POST /payment/webhook) só confirma o recebimento. Rode uma única instância da API, ou use afinidade de sessão. A confirmação por webhook está no roadmap.

16. Fluxos principais

Cadastro e login

  1. O cliente se cadastra em /signup (web) ou em "Crie sua conta" (app), via POST /users, e vira CLIENT.
  2. Contas da equipe são criadas pelo Administrador (web: Equipe; app: Usuários).
  3. Login via POST /auth/login. O front guarda o token e o usuário e envia Bearer nas próximas chamadas.

Pedido com entrega

  1. O cliente vê o cardápio (GET /products), o status da loja e o banner.
  2. Monta o carrinho: quantidade, adicionais, ponto da carne, ingredientes removidos e observação.
  3. No checkout, escolhe ou cadastra um endereço (com busca de CEP). A tela mostra o orçamento de POST /orders/quote.
  4. Paga online (PIX ou cartão, e o pedido nasce PAID) ou escolhe pagar na entrega (dinheiro com troco ou maquininha).
  5. O pedido entra como PENDING no quadro. Cozinha (ou gestão) aceita e marca como pronto.
  6. A gestão despacha para um entregador, ou o entregador pega o pedido. O status vai para DELIVERING.
  7. O entregador confirma a entrega (DONE). Se era pagamento na entrega, vira PAID.

Pedido para retirada

TAKEOUT não exige endereço, não tem taxa e tem tempo estimado de 15-20 min. Depois de pronto, aparece em "Retirar no Balcão", e a gestão marca "Entregue ao Cliente" (READY_FOR_PICKUP → DONE).

Logística

  1. No pedido pronto, a gestão clica em Despachar. A API lista os entregadores (/orders/drivers/list) e sugere pedidos do mesmo bairro (/orders/:id/nearby).
  2. PATCH /orders/:id/assign atribui o entregador e coloca o pedido em DELIVERING.
  3. O entregador vê endereço, mapa, troco a levar e, no app, o botão de ligar para o cliente.

17. Uploads e imagens

  • Produtos (POST/PATCH /products), avatares (POST/PATCH /users) e POST /uploads aceitam JPG, PNG ou WebP de até 5 MB no campo file (um arquivo por envio).
  • O tipo é conferido pelo conteúdo (assinatura do arquivo), e não pela extensão. A imagem é rotacionada conforme o EXIF, limitada a 800 px de largura e convertida para WebP (qualidade 80) com Sharp.
  • Os arquivos ficam em UPLOADS_DIR e são servidos em /uploads/<arquivo>. Produtos guardam só o nome do arquivo, e avatares guardam /uploads/<arquivo>.
  • Um formulário inválido não deixa imagem órfã, e se a operação falhar o arquivo recém-gravado é apagado.
  • POST /maintenance/optimize-images converte imagens antigas (não WebP) de produtos e avatares, mantendo os originais em disco.

22. Limitações conhecidas e roadmap

Limitações atuais

  • Sem recuperação de senha por e-mail: um Administrador define uma nova senha.
  • Atualização por consulta periódica, sem WebSockets (quadro a cada 5 s, Meus Pedidos na web a cada 10 s, status da loja a cada 30 s na web e 60 s no app).
  • Banner de promoções e cupons apenas informativos: não há desconto no checkout.
  • Uma loja por instalação.
  • Registro de pagamentos em memória, e o webhook do Mercado Pago só confirma o recebimento.
  • Sem migrations versionadas.
  • Dados da loja, taxas de entrega e promoções definidos no código.
  • App: sem envio de fotos de produto ou de perfil (feito pela web).

Roadmap

  • Recuperação de senha por e-mail.
  • Status do pedido em tempo real via WebSockets.
  • Notificações push.
  • Cupons e promoções aplicados no checkout.
  • Multi-loja / multi-tenant.
  • Confirmação do pedido pelo webhook do Mercado Pago.
Marca: antes do lançamento comercial, faça a busca no INPI (pePI) e o pedido de registro pelo e-Marcas nas classes 9, 35, 42 e 43. Registre também o domínio comestra.com.br.

23. Troubleshooting

A API não conecta no banco

  • Confirme que o PostgreSQL está rodando. Windows: serviço postgresql-x64-<versão> em services.msc. Linux: systemctl status postgresql.
  • Confirme que o banco existe (psql -U postgres -l) e revise DB_HOST, DB_PORT, DB_USERNAME, DB_PASSWORD e DB_DATABASE.
  • No Linux, a conexão é TCP: o usuário precisa de senha (ou de uma regra trust no pg_hba.conf).

A API não sobe em produção

"JWT_SECRET não definido...": defina JWT_SECRET no ambiente. Com NODE_ENV=production, ele é obrigatório.

Os usuários padrão não entram

  • Rode cd backend && npm run seed para recriar as contas e redefinir as senhas.
  • Confira se SEED_DEMO_USERS não está false e se a API aponta para o banco certo.

A web não acessa a API

  • Abra http://localhost:3000/health. Confira VITE_API_URL e reinicie o npm run dev depois de mudá-la.
  • Com CORS_ORIGINS preenchido, inclua a origem do site (ex.: http://localhost:5173).

O app não acessa a API

  • Celular e computador no mesmo Wi-Fi, porta 3000 liberada no firewall e API rodando.
  • Emulador Android: use EXPO_PUBLIC_API_URL=http://10.0.2.2:3000 se o IP da rede não funcionar.
  • Fora da rede: npm run tunnel (precisa de ssh) e depois npx expo start --tunnel --clear. Se o Serveo cair, reinicie o túnel e o Expo.
  • Depois de mudar qualquer EXPO_PUBLIC_*: npx expo start --clear.

Pedido recusado

  • "A loja está fechada no momento.": abra a loja no painel (Dashboard ou Pedidos) ou via PATCH /store/status com { "is_open": true }.
  • "Somente clientes fazem pedidos e pagamentos...": entre com uma conta CLIENT.
  • "Endereço obrigatório para delivery." / "Endereço não encontrado.": cadastre ou selecione um endereço do próprio cliente.
  • Produto "indisponível" ou "não está mais no cardápio": reative o produto ou tire-o da lixeira.

Pagamento online

  • 503 "Pagamento online indisponível...": configure MP_ACCESS_TOKEN ou ligue o sandbox (desenvolvimento).
  • "Pagamento não encontrado ou expirado...": a API reiniciou entre o pagamento e o pedido. Gere um novo pagamento (no sandbox) ou confira no painel do Mercado Pago.
  • Cartão não carrega na web: o SDK do Mercado Pago precisa de internet. Use PIX ou o pagamento na entrega.

Upload falha

  • Envie um único arquivo no campo file, em JPG, PNG ou WebP de até 5 MB.
  • Verifique a permissão de escrita em UPLOADS_DIR (padrão backend/uploads).

Testes E2E não sobem

  • Informe DB_PASSWORD no ambiente (o reset do banco não lê o backend/.env) e confira se o Google Chrome está instalado.
  • Portas 3001/5174 ocupadas por outra aplicação: libere-as ou use E2E_API_PORT/E2E_WEB_PORT.

Build web ou Expo reclama do Node

Instale o Node.js 22 LTS ou mais recente.
